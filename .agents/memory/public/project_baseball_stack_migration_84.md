3. Copied `db_data` (167MB compressed) via `sudo tar` + SSH pipe (see gotcha below on why not rsync), checksummed both ends to confirm byte-identical transfer.
4. Brought up `db` on `.84` first, then `docker compose up -d --build` for the rest (local Dockerfiles rebuild fine, ~2-3 min).
5. Verified: Postgres row counts identical on both copies (`projections` 275173, `actual_stats` 24265, `player_info` 40, `player_id_aliases` 9, `positional_games` 0) before touching NasHost-01's copy further. All 3 shiny apps return HTTP 200. Scraper has Chrome/chromedriver present.
6. Created the "BB Refresh Stats" DSM Task Scheduler task on `.84` (task ID 3 there — IDs are per-NAS-unit) using the newly-confirmed [[reference_synoschedtask_file_edit]] file-creation technique — 6:45 AM daily, same command. Disabled (not deleted) the original task (ID 8) on NasHost-01, backed up first.
7. Ran the actual `run_refresh_stats.sh` pipeline end-to-end on `.84` as a real test (not synthetic) — clean pass, ~4 min, zero errors, Ryan received the real digest email confirming it.
8. Stopped all 5 containers on NasHost-01 (kept as rollback, not deleted) and renamed its `docker-compose.yml` → `docker-compose.yml.disabled-migrated-to-84` so it can't be accidentally brought back up via a stray `docker compose up`.

## Gotchas hit and fixed (reusable for any future container migration to `.84` or similar)

1. **`rsync`'s remote server mode is blocked on this DSM's SSH, even though SSH key auth succeeds fine.** `rsync -e ssh ...` fails immediately with `Permission denied, please try again` / `connection unexpectedly closed` — verbose SSH debug shows auth succeeds, session opens, the `rsync --server ...` command is sent, then it's rejected. Root cause not fully diagnosed (likely a DSM security wrapper restricting the rsync binary specifically over non-interactive SSH exec — plain `ssh ... "command"` for other commands works fine). **Workaround: use `tar czf - ... | ssh ... "tar xzf -"` streaming instead of rsync for any file transfer TO a Synology box's SSH.** `scp` also failed (`subsystem request failed`) — tar-over-ssh-pipe is the reliable fallback.

2. **Postgres data directory ownership must be numeric-UID-preserved, not just copied.** `sudo tar` preserves ownership in the archive, but if you `chown` the destination for convenience (I initially did `chown Brock:users` to make the extracted files easy to inspect), you break Postgres — the official image runs internally as UID 999, not whatever host user extracted the tarball. **Always check the source's actual numeric ownership (`ls -lan`) and match it exactly on the destination**, don't assume a friendly owner:group is fine for a container-internal data directory.

3. **`.84` has no `docker` group and the socket is `root:root`-only — any script/task that calls plain `docker` (no `sudo`) as a non-root owner will silently fail.** This wasn't caught until running the actual refresh script for real — it calls `docker inspect` directly (matching how it works fine on NasHost-01, which has Brock in a `docker` group, GID 65536, socket `root:docker` mode 660). Fixed by replicating that exact setup on `.84`: `synogroup --add docker Brock` (Synology's own `/usr/syno/sbin/synogroup` — standard `groupadd`/`usermod` don't exist on DSM), `chown root:docker /var/run/docker.sock`, and — since that chown doesn't survive a `dockerd` restart — a small systemd oneshot unit (`docker-socket-group-fix.service`, `After=`/`Requires=pkg-ContainerManager-dockerd.service`, `ExecStart=/bin/chown root:docker /var/run/docker.sock`, enabled) to reapply it automatically every time Docker starts. **Landed on the exact same GID (65536) as NasHost-01 without forcing it — apparently the first custom group DSM assigns on a fresh box.**

4. **`docker` CLI binary path**: `/usr/local/bin/docker` → `/var/packages/ContainerManager/target/usr/bin/docker` → (real binary at `/srv/storage/@appstore/ContainerManager/usr/bin/docker`), then `/usr/bin/docker` → `/usr/local/bin/docker`. Replicated this symlink chain on `.84` (previously I'd only been using the full path directly for ad-hoc commands — this migration is what made `docker` actually need to be on PATH for a script, not just my own interactive commands).

## Two more baseball DSM tasks missed during migration — found AND fixed 2026-08-08
The migration only moved/disabled **"BB Refresh Stats"** (`run_refresh_stats.sh`, 6:45 AM). Two more tasks were missed and both are now fixed:
1. **"BB Refresh Rosters"** (`refresh_2026.sh`, 8:06 AM) — morning Fantrax roster sync + digest prep. Recreated on `.84` as task id 4, verified live in crontab; original disabled + backed up on NasHost-01. Next real test: tomorrow 8:06 AM.
2. **"BB daily digest"** (9 PM nightly) — found while fixing #1, not initially flagged. **This one was worse: it had been reporting `Status: Success` while actually completely broken since Aug 6**, because every `docker exec` in the script is wrapped in `|| true`, masking the real exit code — DSM's own success/fail tracking was lying. Log showed nothing but `Container ... is not running` on repeat. **Ryan had gotten zero nightly baseball digest emails since Aug 6 without any alert.** Recreated on `.84` as task id 5, disabled on NasHost-01.

**Lesson 1:** when migrating a multi-task service off a NAS, enumerate every DSM task referencing its directory/containers up front (`synoschedtask --get`, grep for the app's path) — don't rely on remembering task names from an earlier conversation. A full sweep of all 10 NasHost-01 tasks confirmed no further baseball/migration leftovers after these three.
**Lesson 2:** a DSM task showing `Status: Success` is not proof the underlying script actually worked — if a script swallows errors (`|| true`, `set +e` around the real work, etc.), the task scheduler's status tracking inherits that blindness. Worth a quick script read, not just a status glance, when auditing scheduled jobs after an infrastructure change.

Also found and fixed the same day: NasHost-01's **"movies transfer"** DSM task (ID 5, nightly rsync from the DS1525+ Movies migration) was never disabled after that cutover went live — silently erroring daily since. Unrelated to baseball, same category of leftover-task cleanup gap. Disabled + backed up.

## Not yet done / residual risk
- **NasHost-01's stopped containers have `restart: always` baked into Docker's own container config** (independent of the compose file, which is now renamed/inert). Genuinely unclear whether a full NasHost-01 host reboot would resurrect them despite being manually stopped beforehand — Docker's behavior here varies by version and wasn't tested. If NasHost-01 ever reboots, **check `docker ps` for a resurrected `baseball_db` before assuming `.84`'s copy is still the sole source of truth** — a second live Postgres instance both accepting writes would be a real split-brain risk.

**CONFIRMED — this risk materialized 2026-08-18 ~4:05-4:10 PM PT, and it doesn't even take a full host reboot.** During an unrelated homebridge troubleshooting session, NasHost-01's Docker daemon/Container Manager restarted (NAS itself stayed up the whole time, 41 days uptime unaffected — this was a Docker-level restart only, cause not yet identified). All 5 previously-stopped baseball containers (`baseball_db`, `baseball_shiny_app/pro/dev`, `baseball-scraper-1`) came back up automatically via their baked-in `restart: always` policy, exactly as this memory warned. **A Docker daemon restart is enough to trigger this — a full host reboot isn't required.** As of discovery, not yet resolved — Ryan asked to review before Ivy stops them back down. **If this recurs, check for a resurrected baseball_db immediately and treat as urgent** — flag to Ryan fast, since two live Postgres instances both potentially accepting writes (baseball_db on .82 alongside .84's copy) is a genuine data-divergence risk, not just wasted compute. **FIXED 2026-08-18 ~4:30 PM PT, Ryan-approved.** All 5 containers stopped cleanly (no hangs, 5-16s each) and `docker update --restart=no baseball_db baseball_shiny_app baseball_shiny_pro baseball_shiny_dev baseball-scraper-1` applied — verified individually via `docker inspect ... {{.HostConfig.RestartPolicy.Name}}`, all 5 confirmed `no`. This specific resurrection failure mode (any Docker/Container Manager restart bringing the rollback copy back to life) is now genuinely closed — not just the renamed-compose-file mitigation from the original migration, which only blocked `docker compose up`, not the baked-in per-container restart policy that actually caused this incident.
