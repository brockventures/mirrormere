2026-08-08 ~22:40-22:47 PT: VM crashed unexpectedly (journal: "corrupted or uncleanly shut down") after a full week of uptime (booted 2026-08-01 10:57, prior boot ran cleanly for 7 days). Crashed twice in quick succession — boot lasted only 49s (22:42:20-22:43:09), then crashed again, then came back clean at 22:47:37.

`ivy.service` + `loginctl linger` auto-recovery worked correctly both times — Claude/Discord session came back up on its own each boot, no manual restart needed.

**CORRECTED — my first theory was wrong, Ryan caught it.** I initially guessed Ryan ran `/login` in a separate shell that doesn't inherit the static token. False: `ivy-attach` (`~/.bashrc` alias) is `tmux attach -t claude-channels` — the exact same session/process tree that has `CLAUDE_CODE_OAUTH_TOKEN` wired via `ivy.service`'s `EnvironmentFile=`. Ryan attached to that literal session and still had to `/login`, and confirmed Discord was unresponsive before he did. Root cause found via `strings` on the `claude` binary (v2.1.226): **`CLAUDE_CODE_OAUTH_TOKEN` has no self-heal on 401.** Exact string: "OAuth 401: keeping the user-supplied CLAUDE_CODE_OAUTH_TOKEN instead of adopting the stored credential. Mint a fresh token with `claude setup-token` and restart with it, or unset the variable and run /login." So once the static token starts getting rejected, the CLI keeps retrying the dead token forever instead of falling back to the shared-credentials-file refresh flow — silent API failure, looks exactly like "not responsive on Discord" from outside. This is a real regression vs. pre-Tier-2 behavior (shared-credentials-file approach self-heals; static token does not). Could not confirm the literal 401 in tmux scrollback (buffer had rolled past it by the time I checked), so *why* the token died is still unknown — only the stuck-retry mechanism is confirmed. See [[project_oauth_setup_token_fix]] for the original Tier 2 design — this finding should be folded into that memory's tradeoffs section.

**Proposed to Ryan 2026-08-08 ~23:05 PT, then walked back ~23:26 PT.** Initially proposed minting a fresh static token. Ryan pushed back ("the current one is working") — checked and he was right: the `claude` process running since right after the crash (PID 569) has had the *same* static token in env the whole 39+ minutes, unchanged, and precedence puts it above `/login` creds — so if it were really dead, it would still be failing now, and it isn't. **No hard evidence the token itself ever died.** The "OAuth 401: keeping the user-supplied token" binary string is a real, confirmed CLI behavior, but I never actually observed that message fire for this token — I inferred it from a plausible mechanism, not a confirmed cause. Best guess now: tonight's outage was a transient issue (cloudflared/network hiccup was logged 22:52:32-51, right in this window) that self-resolved, and Ryan's `/login` coincided with recovery rather than causing it. **Lesson: verify a "credential is dead" claim against the actually-running process's current behavior before recommending a fix — don't reason from mechanism alone.** No token refresh needed; only follow-up is adding detection for the real stuck-401 state in case it ever genuinely occurs.

If it recurs, treat as a pattern worth deeper investigation (distinct from [[project_ivy_network_flapping]], which is cloudflared QUIC drops without a full VM reboot).
