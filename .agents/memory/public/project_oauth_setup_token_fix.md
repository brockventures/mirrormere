Researched 2026-08-03 in response to [[project_oauth_outage_2026-08-03]]. `claude setup-token` (v2.1.221) mints a static OAuth token, subscription-backed (no API/console billing), valid 1 year, does NOT persist to `~/.claude/.credentials.json`. Setting `CLAUDE_CODE_OAUTH_TOKEN=<token>` in a process's env makes it short-circuit the credential accessor entirely — no refresh token, no expiry tracking, can never redeem/rewrite the shared file. That's true process isolation from the single-use-refresh-token race (still present and unpatched as of 2.1.221 despite `proper-lockfile` locking already in the binary — locking wasn't enough, today's outage happened with it in place).

**Tier 1:** wire the token into the 7 systemd timers only (via `claude-locked.sh` or `EnvironmentFile=`), leaving `ivy.service` completely untouched. Zero risk to the live Discord session. Does not fix the background-agent-vs-interactive-session collision (the likely actual cause of the 08-03 outage).

**Tier 2 — Ryan's chosen direction (2026-08-04): "tier 2 seems like the right thing to do."** Also adds the token to `ivy.service`'s own environment so the interactive session + everything it spawns (including background agents) stops touching the shared file — fully closes the race, takes effect at next natural restart (not disruptive to apply). Tradeoffs: hard 1-year expiry with no self-healing (would need a dated reminder + expiry canary), and the token's scope is inference-only.

**Scope-impact check completed 2026-08-04** (background agent, read-only, binary-strings analysis of 2.1.221): `/code-review ultra`, Remote Control, and Projects are all confirmed **blocked** by inference-only scope but **safe for Ivy** — CLAUDE.md already says Ivy never launches ultrareview itself, and Ivy doesn't use Remote Control/Projects. One caveat flagged to Ryan: if he ever runs `/code-review ultra` from *inside* the live Discord session itself (not a separate terminal), that would break post-Tier-2. **Artifact publishing is the one unresolved question** — routes through an account-scoped endpoint but no explicit scope-gate string was found either way; recommended a cheap live test (publish a throwaway artifact under a temp `CLAUDE_CODE_OAUTH_TOKEN`-set shell) before shipping Tier 2. MCP tools, heartbeat, Discord replies, background-agent spawning are all plain inference — confirmed safe.

**REGRESSION FOUND 2026-08-08, see [[project_ivy_vm_crash_2026-08-08]] for full incident.** Tier 2's static token has no self-heal on 401 — confirmed via `strings` on the v2.1.226 binary: "OAuth 401: keeping the user-supplied CLAUDE_CODE_OAUTH_TOKEN instead of adopting the stored credential... unset the variable and run /login." Once the static token starts getting rejected, Claude Code keeps retrying it forever instead of falling back to the shared-credentials-file refresh flow that self-healed pre-Tier-2 — manifests as silent Discord unresponsiveness (process alive, API calls failing) until someone manually attaches and runs `/login`. This directly trades away the self-healing property that was the whole point of the original (pre-Tier-2) design.

**Confirmed against official docs 2026-08-08** (code.claude.com/docs/en/authentication, fetched via curl per CLAUDE.md's curl-over-WebFetch rule): documented precedence is cloud-provider > `ANTHROPIC_AUTH_TOKEN` > `ANTHROPIC_API_KEY` > `apiKeyHelper` > `CLAUDE_CODE_OAUTH_TOKEN` > subscription `/login` OAuth — no automatic fallback between tiers on failure. Only `/login`-based subscription OAuth has documented self-healing (auto refresh) and expiry warnings ("Renewing early matters most for sessions that run unattended... stops making progress once the credential expires and can't recover until you sign in again" — that warning system is specific to `/login` creds, not the static token). This is by-design CLI behavior, not a misconfiguration on our part.

**Revert complication:** background agents spawned from the interactive session inherit `ivy.service`'s env. A full revert (pulling `EnvironmentFile=` from `ivy.service`) would put BOTH the interactive session and every spawned background agent back onto the single shared `~/.claude/.credentials.json` — recreating the exact concurrent-refresh-token race from the original [[project_oauth_outage_2026-08-03]] that Tier 2 was built to eliminate. Not a clean fix either way.

**CONFIRMED REAL BREAKAGE 2026-08-08 ~23:30 PT — background-agent spawning is broken under the static token.** Spawned a background agent (`ha-smartthings-verify`, general-purpose, model opus) from the live Discord session; it died immediately with `401 Invalid bearer token · Please run /login`. Verified via `/proc/<pid>/environ` that the subagent process had the byte-identical `CLAUDE_CODE_OAUTH_TOKEN` as the main session (md5 matched exactly) — the main session was working fine with that same token at the same moment. So the token itself is not dead; agent-spawning specifically fails under it. The failed process was launched with `--agent-id ... --team-name ... --parent-session-id ...` flags, suggesting agent orchestration uses a session/team-coordination layer resembling Remote Control — which the official docs explicitly say the static setup-token **cannot** establish ("It can only make model requests, so it can't establish Remote Control sessions"). This directly **contradicts** the 2026-08-04 "Scope-impact check" in this same memory (above), which concluded background-agent spawning was "confirmed safe" — that check was wrong (or something changed since 2.1.221 → 2.1.226). Reproducible: identical token, main session passes continuously, subagent spawn fails instantly. Since nearly all of Ivy's real work runs through spawned background agents (CLAUDE.md Route 2/3/4), this is a functional break of a core capability, not a cosmetic issue. **Proposed to Ryan: revert Tier 2 on `ivy.service` now** — the background-agent breakage outweighs the crash-time refresh-token race Tier 2 was protecting against. Awaiting his go-ahead as of 2026-08-08 23:35 PT.

**Walked back 2026-08-08 ~23:26 PT — no token refresh was actually needed.** Ryan questioned why a fresh token was necessary if the current one was working; verification showed the running `claude` process had kept the same static token in env the entire outage window and was functioning fine, meaning the token was never confirmed dead — see [[project_ivy_vm_crash_2026-08-08]] for the full self-correction. The 401-no-self-heal mechanism (still confirmed real via binary strings + official docs) remains a legitimate latent risk, just not what happened tonight. Only follow-up: add monitoring that can detect the real stuck-401 state if/when it actually occurs, rather than relying on the CLI to recover on its own.

**Context on today's canary alert (2026-08-04, 9:00 AM PT, "36 min expired"):** confirmed this was an ordinary self-healing TTL gap, not a repeat of 08-03's collision/corruption bug — token expired naturally ~1:24 AM with nothing running until the 2:00 AM heartbeat refreshed it cleanly (credentials file got a normal fresh write, not the ~0-reset corruption pattern from 08-03). No manual `/login` needed. Tier 2 would also eliminate this alert category, since a static token has no such gap.
