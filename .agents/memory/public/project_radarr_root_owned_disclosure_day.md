Found during 2026-08-17 nightly NAS log review: Radarr logged **1039x** `UnauthorizedAccessException: Access to the path '/data/media/movies/Disclosure Day (2026)/...mkv' is denied` (+ matching `IOException: Permission denied`), plus 520+519 `ImportApprovedMovie: Couldn't import movie` warnings for two different downloaded release files of the same title — all one root cause, retried every import-scan cycle over 24h.

**Root cause:** on the NAS filesystem (`/mnt/storage/media/movies/Disclosure Day (2026)/`), both the movie folder and the existing `.mkv` inside it are owned by **root:root** (`drwxr-xr-x` / `-rw-r--r--`) instead of Radarr's own PUID:PGID (**1026:100**, per the container's env). Radarr runs as uid 1026 — not root, no write access via the `other` bits — so every attempt to move/replace/delete that file for a new import fails outright. Same general class of bug as [[project_kometa_root_files]] (historic root-run leaving root-owned files behind) — likely this file was placed there by a manual root-context operation (SSH copy, root-run script, or similar) rather than through Radarr's own normal import path.

**Fixed 2026-08-18:** ran `sudo chown -R 1026:100 "/mnt/storage/media/movies/Disclosure Day (2026)"` directly on NasHost-01 via SSH. Verified with `ls -lan` before/after — folder + `.mkv` both changed from `0 0` (root:root) to `1026 100`, matching every other movie folder. Went through cleanly; a flagged concern beforehand (this path is NFS-mounted from AppHost-02 since the Movies migration, and that export is known to reject chown/chgrp for root-squash reasons — see [[feedback_nfs_primary_gid_only]]) turned out not to apply, since the chown ran through the NAS's own local SSH/sudo session on the export side, not through a client-side NFS mount. No Radarr restart needed — next import scan should pick it up normally.

**How to apply:** if a similar single-title `UnauthorizedAccessException` shows up for a different movie in future reviews, check ownership of that specific file/folder the same way before assuming it's a new/different bug — this looks like a one-off stray root-owned item, not a systemic NFS/ACL issue. If the chown needs to run *through* the NFS-mounted path (e.g. from a client, not the export-side host) rather than directly on NasHost-01/AppHost-02, root-squash could still bite — not yet tested that direction.

**Confirmed still holding, 2026-08-19.** The 28x occurrences of this exact error visible in the 08-19 nightly review's 24h log window are all timestamped 04:53-04:58 UTC on 08-19 (21:53-21:58 PT on 08-18) — i.e. the tail end of the same pre-fix burst that prompted the chown (applied ~22:02 PT the same night), not a new recurrence. Zero occurrences in the ~23 hours since. Live check: folder + file both `1026:100`, only one file present (the upgraded Bluray release, the old WEBDL release is gone). Fix holds — don't re-flag this again unless a *new* timestamp shows up after 2026-08-18 22:02 PT.

**New occurrence, different title, 2026-08-21 nightly review — same bug class, NOT the Disclosure Day fix regressing.** Radarr logged 1011x `UnauthorizedAccessException`/`Permission denied` for `/data/media/movies/Backrooms (2026)/Backrooms (2026) {imdb-tt26657236} [AMZN][WEBDL-1080p][EAC3 5.1][h264]-playWEB.mkv`, trying to import a newly-downloaded BluRay upgrade over it. Verified live via `ls -lan`: both the folder and the existing WEBDL `.mkv` are owned **root:root (0:0)**, not Radarr's `1026:100`, exactly the Disclosure Day pattern. Confirmed this is genuinely a different file/title, not a stale timestamp from an old burst — not yet fixed as of report time. **Fixed 2026-08-22 ~00:41 PT** (Ryan approved same night the review posted): ran `sudo chown -R 1026:100 "/mnt/storage/media/movies/Backrooms (2026)"` via `ssh -p 22 -i ~/.ssh/id_ed25519 deploy@app-host` (per [[project_media_stack]]/DOCKER_PLAYBOOK.md — note: plain `ssh NasHost-01` with no port/key/user fails, must use the full form). Verified via `ls -lan` before/after: folder + `.mkv` both changed from `0 0` (root:root) to `1026 100`. No restart needed. This confirms the "how to apply" note above — check ownership per-title rather than assuming systemic NFS/ACL breakage; likely another stray manual-root-context file drop. Two occurrences now (Disclosure Day 08-18, Backrooms 08-21/22) — same fix each time, low effort, keep treating as one-off per-title strays unless a third shows a common source (e.g. same download client/script).

**Likely origin, investigated 2026-08-22:** Ryan asked why files land root:root in the first place. Checked SABnzbd's own "complete" staging folder — correctly `1026:100`, ruling out the download client. The movies library path is NFS-mounted from AppHost-02 (.84), populated by the Movies migration's rsync ([[project_second_nas_ds1525]]), which ran as root via a DSM scheduled task and deliberately dropped `-a`'s owner/group preservation (root-squashed NFS rejected chown/chgrp). Backrooms' stray `.mkv` has a file timestamp of **2026-07-13 19:36** — the exact day DS1525+ was powered off mid-migration (RMA/degraded-pool incident). Strong circumstantial match: either the interrupted rsync or a manual root SSH copy during that outage's diagnosis left it root:root, and it just sat unnoticed until Radarr tried to import an upgrade over it now. Not confirmed with certainty (no server logs reaching back that far), but the timestamp coincidence is compelling. **If a future occurrence has a recent file timestamp (well after the migration window, which closed 2026-08-05), that would rule out this explanation and point to something still actively creating root-owned files — investigate the download/import pipeline itself at that point.**
