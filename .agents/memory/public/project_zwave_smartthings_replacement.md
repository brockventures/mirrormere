Ryan decided 2026-08-09 not to pay Samsung's $4.99/mo SmartThings API fee (starts Oct 2026, see [[project_ha_samsung_tv_ir]] for the TV side of this same decision) and wants to fully replace SmartThings with a direct Z-Wave connection for his 3 blind devices (`cover.living_room_blinds_1`, `cover.living_room_blinds_2`, `cover.bedroom_blinds` + 3 battery sensors).

**Blinds identified:** Springs Window Fashions RSZ1 (Bali/Graber "Virtual Cord" motor), mfr `0x026E`, type `0x5253`, id `0x5A31`, joined non-secure Z-Wave (`ZWAVE_LEGACY_NON_SECURE`), confirmed via SmartThings API device metadata. Already in Z-Wave JS's supported device database (`devices/0x026e/rsz1.json`) — no custom config needed. Battery-powered = sleeping FLiRS nodes, don't repeat the mesh.

**Why network-attached, not USB-into-NAS:** Checked the existing Zigbee setup as precedent — ZHA connects to an SMLIGHT SLZB-06P7 over Ethernet (`socket://10.0.0.x:6638`), NOT a USB dongle. The HA docker-compose on NasHost-01 (`/mnt/NasHost-01/docker-compose.yml`) is `network_mode: host` with no `devices:` USB passthrough configured anywhere (only a commented-out rtl_433 block). DSM 7.3 also dropped the `cp210x`/`cdc_acm` USB-serial kernel modules HA would need for direct USB passthrough — re-adding them via Package Center is a fragile, breaks-on-DSM-update path. So the recommended approach mirrors the Zigbee pattern: network-attach the Z-Wave radio instead of plugging it into the NAS.

**Hardware recommendation (prices as researched 2026-08-09, not locked in):**
- Home Assistant Connect ZWA-2 (800-series, Z-Wave Long Range, built by the Z-Wave JS team) — $52.95-68.95 (ameriDroid)
- Budget alt: Zooz ZST39 LR (also 800-series LR) — $23.95-26.95 (Smartest House/ameriDroid)
- Pair with an SMLIGHT SLZB-U2L (same vendor as the existing Zigbee bridge) to put the radio on Ethernet instead of USB
- Plus a USB extension cable regardless, to keep the radio away from RF interference

**Software approach:** run a `zwave-js-ui` companion Docker container alongside HA (same shape as the existing matter-server/otbr companion containers) — Docker HA here is non-Supervised, so there are no Supervisor add-ons. Point HA's `zwave_js` integration at the `zwave-js-ui` container's websocket.

**Migration process per shade (~10 min each):** exclude from SmartThings (new HA Z-Wave controller can do the excluding, SmartThings doesn't need to be involved) → hold the shade's program button ~7s to exclude (LEDs flash green then orange) → put Z-Wave JS UI in include mode → hold program button ~3s to include (LED flashes green). **Entity IDs will change** from the old `cover.living_room_blinds_*` names — anything referencing them (the cover group at configuration.yaml:268-272, 4 dashboard cards, see [[project_ha_samsung_tv_ir]]) needs updating post-migration.

**Recommended sequencing:** order hardware → stand up zwave-js-ui, confirm healthy controller → migrate bedroom shade first as canary → migrate the other two → update automations/dashboards → only then remove the SmartThings integration entirely.

**Risk:** each shade is briefly uncontrollable via HA between exclude and include, but the physical remote works the whole time — no real lockout risk. If a shade won't exclude cleanly, Z-Wave JS's "remove failed node" clears the ghost node. Don't decommission SmartThings until all 3 shades are verified working — rollback means re-including to the SmartThings hub.

**Non-issue already cleared:** the SmartThings config entry also contains the (unused) official TV entity and a second offline TV — removing SmartThings does NOT cost any live TV functionality, already confirmed via the [[project_ha_samsung_tv_ir]] dependency check.

**Clarified 2026-08-09 10:27 PT — why 2 pieces of hardware, and why existing SMLIGHTs can't substitute.** Ryan asked if one of his 2 existing SMLIGHT units (SLZB-06P7 Zigbee coordinator at .253, SLZB-06P7-thread RCP at .79/.204, see [[project_matter_ikea]]) could run Z-Wave in "dual mode." No — confirmed via SMLIGHT's own product docs: both existing units are built on a Texas Instruments CC2652P7 chip, 2.4GHz-only (Zigbee+Thread coexist on it fine, that's what the MR-series markets as "multiradio," but that's Zigbee+Thread, not Z-Wave). Z-Wave is sub-GHz (~908MHz US), needs entirely different radio silicon — not a firmware switch, a hardware limitation. Also these are integrated coordinator boards, not USB-stick hosts, so there's no spare port to plug a Z-Wave stick into. The SLZB-U2L (confirmed via smlight.tech/product/slzb-u2l) is a genuinely different product category — no onboard radio at all, purely a USB-to-Ethernet bridge; its only job is letting a USB stick (Zigbee OR Z-Wave OR Thread OR LoRa) be reached over the network instead of plugged directly into a computer. It has room for 2 USB sticks simultaneously (useful to know for future expansion, not relevant to migrating the existing Zigbee/Thread hardware). So the shopping list is genuinely 2 items: the Z-Wave radio itself (required, nothing owned does Z-Wave) + the U2L bridge (recommended but skippable if Ryan accepts plugging into the NAS directly and dealing with DSM's USB-serial driver situation).

**CORRECTED 2026-08-09 13:37 PT — SLZB-06U recommendation was wrong, Ryan caught it.** Claimed the $40 SLZB-06U was a valid U2L substitute based on cloudfree's generic product-family blurb, without checking actual port layout. Ryan correctly pushed back: "the slzb-06u does not have a usb port." Verified via SMLIGHT's own spec sheet (smlight.tech/product/slzb-06u/): the 06U has exactly ONE USB-C port total, shared between power input and passthrough — no dedicated USB-A host port, no adapter cable in the box. Not a real substitute. **Lesson: verify exact port count/type from the manufacturer's spec table, not shared marketing copy across a product family — a listing describing "the 'U' models" collectively doesn't mean every port claim applies identically to every SKU in that family.**

**Real verified alternative found:** SMLIGHT SLZB-MRW10U ($65, 71 in stock, cloudfree.shop) — confirmed via the actual MRxU family spec table ("USB-C · USB-A passthrough" listed as two distinct physical ports) that this one has a genuine dedicated USB-A host port separate from its USB-C power input. Downside: it's also a multi-radio Zigbee+Thread board Ryan doesn't need (already has dedicated units), so he'd be paying for unused radio hardware — but the passthrough port itself is real this time.

**Why the U2L is hard to find:** confirmed via SMLIGHT's own product page — it's brand new (revision "r1.03 · 2026-08," released this month), sold through distributors rather than direct checkout, so reseller stock hasn't caught up. Not discontinued — likely to become available at more resellers within weeks. Presented as a valid "wait it out" option alongside the MRW10U.

**Community research on MRxU + external Z-Wave stick reliability, 2026-08-09 13:45 PT.** Ryan asked if people actually run SMLIGHT's non-certified Z-Wave in the wild. Two distinct questions, answered separately:
- **Onboard non-certified Z-Wave radio (built into MRW10U itself):** no independent user reports found anywhere — only SMLIGHT's own "stable in internal testing" marketing claim. Unverified by real users.
- **USB-A passthrough hosting an external stick (the actual plan — ZWA-2 plugged into an MRxU board over network):** real community thread found (community.home-assistant.io/t/setup-slzb-mr1u-to-use-usb-z-wave-adapter/929606) — multiple users confirm MR1U+ZWA-2 works, but with real caveats: (1) RSSI/interference near the board affects the Z-Wave stick, one user needed a longer cable/more distance and still saw ~100ms added latency vs. direct connection; (2) a user reported 2026-02 that any SLZB-OS firmware newer than v3.1.4 causes the serial link to hang randomly — pinned to old firmware as the only workaround, thread went quiet after with no confirmed fix (open issue as of this research); (3) one user (2026-01) couldn't get it working at all after days of trying, called SMLIGHT support unhelpful. Separately, community.home-assistant.io/t/slzb-mr3-frequent-adapter-resets/933809 (35 posts) shows a pattern of general firmware-stability complaints on the newer multi-radio MRxU line (worse than the older single-radio SLZB-06) through late 2025.
- **Verdict given to Ryan:** real and workable for several people, not vaporware, but not "just works" — live unresolved firmware regression risk, plus latency/interference concerns for a timing-sensitive protocol. Reasonable bet for non-critical use (blinds), not a sure thing.

**"If starting fresh, is there one device for Zigbee+Thread+Z-Wave" — researched 2026-08-09 14:02 PT, no such certified product exists.** Checked broadly, not just SMLIGHT. SMLIGHT's own flagship (SLZB-Ultima, launched this same month, Aug 2026 — modular, dual onboard Zigbee+Thread radios + optional Z-Wave 800 add-on) still explicitly labels its Z-Wave add-on "non-certified yet, but ongoing" — same gap as the cheaper MRW10U, even on their premium/pro-market hardware. Other tri-radio-labeled products found (Z-Station from z-wave.me, ESP32 gateways) select one protocol at a time via firmware rather than running all three simultaneously. **Conclusion given to Ryan: the industry hasn't solved certified single-box tri-protocol yet** — likely because Z-Wave chip certification (Silicon Labs) is more locked-down than Zigbee/Thread. Realistic modern setup is still a dedicated Zigbee/Thread box + separate certified Z-Wave stick, at best consolidated via USB passthrough onto one multi-radio board rather than a genuine single SKU.

**No Z-Wave certification ETA found, researched 2026-08-09 14:06 PT.** Checked SMLIGHT's own pages (SLZB-Ultima, dedicated Z-Wave 800 add-on page), an independent in-depth review (smarthomescene.com's SLZB-Ultima review), and attempted the Z-Wave Alliance certification portal (JS-rendered, couldn't query directly). No published date/quarter anywhere — consistently "still working through it," no target given. Useful independent-reviewer clarification worth remembering: "non-certified" is a regulatory/paperwork status per the SmartHomeScene review, not a functional limitation — "behaves like any other Z-Wave 800 controller" in practice; certification mainly matters for professional/commercial deployments. Real risk is the newer-hardware firmware immaturity already documented above (the MR1U/ZWA-2 thread issues), not the certification paperwork itself. Recommended to Ryan: don't plan around an ETA that doesn't exist; the certified ZWA-2 stick he's already buying is the lower-risk path regardless.

**Bridge alternatives beyond SMLIGHT, researched 2026-08-09 14:13 PT.** Ryan asked for non-SMLIGHT options to get the ZWA-2 on the network. Two real alternatives found in HA community usage:
- **Raspberry Pi + ser2net (DIY):** the community-standard approach — cheap (~$15-40), plug ZWA-2 into a Pi, run ser2net to expose it as TCP serial, point Z-Wave JS at that IP. Very well-proven ("hundreds if not thousands" of users per one HomeSeer-forum poster); more setup effort than a plug-and-play box but no dependency on newer/less-tested hardware.
- **HomeSeer Z-NET (G8 or PRO):** a genuinely different-shaped option — purpose-built network-connected Z-Wave controller with the radio built in, no separate USB stick needed. Sold on Amazon/HomeSeer's store, explicitly HA-compatible. Could replace the ZWA-2 purchase entirely rather than bridging it. Price not cleanly confirmed (site's price widget is JS-rendered, didn't get a clean pull) — Ryan needs to check current pricing directly.
- Three paths now on the table: SMLIGHT bridge (MRW10U, in stock, real but firmware-immature per earlier research) + ZWA-2; Pi+ser2net+ZWA-2 (most proven, most DIY); or HomeSeer Z-NET standalone (simplest single purchase, replaces the stick entirely).
